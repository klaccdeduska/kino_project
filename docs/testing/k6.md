## 1. About k6

k6 is a load testing tool used to measure the performance,
stability and reliability of APIs under concurrent load.

It provides metrics such as:

- Average response time
- Median response time
- P95 and P99 latency
- Requests per second
- Failed HTTP requests
- Successful checks
- Virtual users (VUs)

The tool was added to the project using Docker Compose.
The tested k6 version was 2.4.0.

## 2. Test Scenario

The selected scenario simulates multiple cinema customers
requesting the screening schedule of the same movie.

Tested endpoint:

```http
GET /api/movies/:id/sessions
```

This represents a situation where a popular movie premiere
attracts many customers at the same time.

The endpoint retrieves upcoming screenings from MariaDB,
joins the sessions and halls tables, filters the results
by movie ID and start time, and sorts them chronologically.

## 3. Project Architecture

The following technologies are involved:

- NestJS
- MariaDB
- mysql2
- Prisma
- Docker
- k6

Prisma is used to generate the test dataset.
The existing API uses mysql2 to execute database queries.

## 4. Test Dataset

A separate load testing seeder was created:

`backend/prisma/seed-load.ts`

The generated dataset contains:

| Entity | Generated records |
|---|---:|
| Movies | 500 |
| Halls | 20 |
| Sessions | 10000 |

Each generated movie has 20 screenings.

All generated movies and halls use the `[LOAD]` prefix.

The seeder preserves existing records and checks whether
the test dataset already exists before inserting new data.

The tested movie ID was 13. This ID may be different
on another development machine.

## 5. Installation and Setup

Docker must be installed and running.

Start the local database and Redis:

```bash
docker compose up -d db redis
```

Download the k6 Docker image:

```bash
docker compose --profile testing pull k6
```

Verify the installation:

```bash
docker compose run --rm k6 version
```

Configure the backend environment to use the local Docker
database on port 3308.

The DATABASE_URL and DB_* variables must point to the same
local database and use matching credentials.

Install backend dependencies and generate the Prisma client:

```bash
cd backend
npm ci
npm run prisma:generate
```

Ensure the database schema and standard movie seed are
already initialized before generating the load dataset.

Generate the load testing dataset:

```bash
npm run prisma:seed:load
```

Start the backend:

```bash
npm run start:dev
```

## 6. Running the Test

Open another terminal in the project root.

Find a generated movie with upcoming screenings:

```sql
SELECT
    m.id,
    m.title,
    COUNT(s.id) AS session_count
FROM movies m
JOIN sessions s ON s.movie_id = m.id
WHERE m.title LIKE '[LOAD]%'
  AND s.starts_at > NOW()
GROUP BY m.id, m.title
ORDER BY session_count DESC, m.id
LIMIT 5;
```

Verify the API endpoint:

```bash
curl -i http://localhost:3000/api/movies/13/sessions
```

Replace 13 with the generated movie ID if necessary.

Inspect the test script:

```bash
docker compose run --rm k6 inspect /scripts/k6-sessions.js
```

Run the load test:

```bash
docker compose run --rm -e MOVIE_ID=13 k6 run /scripts/k6-sessions.js
```

Save the results:

```bash
mkdir -p docs/testing/results

docker compose run --rm -T -e MOVIE_ID=13 k6 run \
  /scripts/k6-sessions.js 2>&1 \
  | tee docs/testing/results/k6-baseline.txt
```

## 7. Load Profile

The test runs for approximately 120 seconds.

| Duration | Target virtual users |
|---|---:|
| 10s | 10 |
| 20s | 10 |
| 10s | 50 |
| 20s | 50 |
| 10s | 100 |
| 30s | 100 |
| 20s | 0 |

Each virtual user sends a request and waits for one second
before repeating the operation.

## 8. Success Criteria

The following thresholds were configured:

- P95 response time below 500 ms
- Failed HTTP requests below 1%
- Successful checks above 99%

The test also verifies that the API returns HTTP 200
and a non-empty array of screenings.

## 9. Database Optimization

The original query filtered screenings using movie_id
and starts_at and sorted them by starts_at and id.

The original database index contained only movie_id.

A composite index was added to the Prisma schema:

```prisma
@@index([movieId, startsAt], map: "idx_sessions_movie_start")
```

Migration:

`backend/prisma/migrations/4_add_sessions_composite_index/migration.sql`

The index definition is:

```sql
CREATE INDEX idx_sessions_movie_start
ON sessions (movie_id, starts_at);
```

The query execution plan was inspected before and after
adding the index.

### EXPLAIN Comparison

| Metric | Before | After |
|---|---|---|
| Access type | ref | range |
| Index | movie_id | idx_sessions_movie_start |
| Key length | 4 | 9 |
| Estimated rows | 20 | 20 |
| Extra | Using where; Using filesort | Using index condition |

The composite index removed the additional sorting step
and allowed MariaDB to use an index range condition.

MariaDB also removed the previous supporting movie_id
index in the tested database.

### Migration Note

The local database already contained tables, but the
previous Prisma migrations were not registered as applied.

To preserve the existing dataset, the new index migration
was executed separately against the local database:

```bash
cd backend

npx prisma db execute --file \
  prisma/migrations/4_add_sessions_composite_index/migration.sql
```

This command does not register the migration in Prisma's
migration history.

The existing migration history and schema differences
must be reconciled before a normal migration deployment.

On a correctly initialized database with an up-to-date
migration history, use the standard Prisma migration
deployment process instead.

## 11. Analysis

The composite index improved the database execution plan
by removing the additional filesort operation.

However, the API-level performance did not improve
significantly in the measured tests.

The average response time increased from 15.01 ms
to 15.39 ms, while P95 latency increased from 28.68 ms
to 32.38 ms.

Throughput remained almost unchanged, and both tests
completed without failed HTTP requests.

A possible explanation is that the original movie_id
index was already efficient for this workload.

Although the dataset contains 10000 generated screenings,
each tested request retrieves only 20 screenings.

Sorting such a small result set requires little work.

API latency also includes database connection handling,
application processing, network communication and JSON
serialization.

Only one recorded run was performed for each configuration.
Therefore, the observed latency differences cannot be
attributed solely to the new index.

## 12. Conclusion

The cinema API successfully handled a load of up to
100 concurrent virtual users without HTTP request failures.

Both configurations achieved P95 response times well
below the configured 500 ms threshold.

The composite index improved the SQL execution plan but
did not demonstrate an API-level performance improvement
under the tested workload.

No critical performance bottleneck was identified within
the selected load profile.

Future tests could include:

- More screenings per movie
- A higher number of concurrent users
- Repeated benchmark runs
- Redis caching for frequently requested screenings
- Database connection pool monitoring
- CPU and memory usage monitoring

## 13. Safety

All load tests were performed against a local NestJS API
connected to a local Docker MariaDB database.

No shared, production or cloud databases were used.
